# Diagnostic scenario harness

Sprint 9 validates the existing diagnosis pipeline using controlled source data.
It does not add diagnosis rules, adapters, protocols or MCP tools.

## Run and interpret

From the repository root, using the project's Python environment:

```powershell
& .\.venv\Scripts\python.exe -m pytest -m diagnostic_scenarios -q
& .\.venv\Scripts\python.exe -m pytest -m golden --scenario-acceptance -q
& .\.venv\Scripts\python.exe -m pytest tests/scenarios -q
```

The first command validates regression contracts and writes
`sprint9-scenarios.json.tmp` (an ignored derived artifact). The last command also
checks harness behavior, security and real in-process MCP calls. The golden
command is the strict diagnostic acceptance gate: it requires scenario PASS.
Currently four of six golden cases fail acceptance; see the
[Sprint 9 report](sprint-9-validation.md).

Default regression tests compare actual failed semantic assertions to the explicit
`known_gaps` list. An unexpected regression **or improvement** fails this baseline
comparison and requires review. Known gaps are never converted into PASS in
ScenarioResult or DiagnosticValidationReport; no xfail/skip conceals them.
Passing pytest regression contracts does not establish diagnostic acceptance.
Use `--scenario-acceptance` to require PASS for every selected diagnostic case.

## Data and execution

`tests/scenarios/diagnostic-cases.yaml` is a bounded, declarative list of typed
profiles and ExpectedDiagnosis values. It is parsed and validated before running
any case; unknown profiles, unsupported modes, duplicate IDs and contradictory
expectations are rejected. Profiles build canonical FailureScenario values with
the existing RuntimeSnapshot, CorrelationQuery, ProbesConfig, ProbeResult and
log/metric/span observation models. Topology, events and symptoms reuse these
contracts instead of introducing another representation.

ScenarioRunner accepts an injected application factory and calls Runtime.execute
through existing context/authorization checks: diagnose, cached virtual trace,
probe planning/execution, then observability enrichment and re-evaluation.
Only source composition is fake. The existing 3scale semantic adapter, topology,
correlation, evaluator, candidate selection and safe plan remain authoritative.
Tests use fixed UTC time, fixed probe timing, fake Kubernetes resources/runtime,
in-memory observability and a fake probe executor. A socket guard rejects real
network access. No sleeps, cluster or Prometheus instance are required.

Five scenarios additionally invoke the real FastMCP Client. Its driver builds a
cached trace through `plan_probes(troubleshooting_id=...)` and `explain_trace`,
then reuses that plan. The public `trace_resource` tool requires a query; the
driver does not pass the service-only troubleshooting ID to it. MCP diagnosis
uses its configured 900-second window, matching the fixed fixture window.
No second runtime snapshot or alternative diagnosis implementation is introduced.

## Assertions and reports

ExpectedDiagnosis expresses required, rejected, allowed and forbidden hypothesis
identifiers; qualitative confidence; recommendations by required evidence ID;
probe status/facts; evidence categories; unresolved reference kinds; expected
authorization failure; inconclusive/partial results; and bounded evidence counts.
`may_include` is descriptive and imposes no requirement. Recommendations are
matched on the diagnosed subject, not unrelated dependency steps.

Every candidate must reference supporting evidence with provenance/checksum.
Trace hops, targets and probe evidence retain provenance. Plans must be passive,
read-only and neither executable nor executed. Contradiction and historical
context checks prevent an old incident or untrusted text from overriding current
facts. Secret checks inspect canonical diagnosis/trace and captured logs. If a
secret regression is detected, the report omits unsafe actual/trace payloads
while retaining the failed assertion; it does not rewrite evidence checksums.

ScenarioResult carries PASS/FAIL, expected and actual canonical diagnosis/trace,
matched and failed assertion IDs, evidence count and false-positive/negative
counts. Actual diagnosis already includes hypotheses, candidate evidence,
confidence and recommendations. DiagnosticValidationReport aggregates results,
golden counts and expected-inconclusive counts without inventing an accuracy
score. The report test reuses completed results; filtered runs describe only
their selected subset. The JSON file is regenerated by the full marker suite.

False negatives count missing required support/detection assertions; false
positives count forbidden/promoted rejected hypotheses and forced conclusions
in inconclusive cases. Recommendation failures remain scenario failures but do
not inflate either count. Mutation tests verify these controls and safe report
handling independently of the diagnosis engine.

## Adding a scenario and future laboratory execution

Add a small typed profile only when canonical fixture composition needs it, then
declare expectations in YAML. Reuse existing fake providers and fixed clock.
Do not weaken expectations or change approved rules to make the report green.
Golden cases should remain a small mandatory diagnostic gate in future sprints.

Only `mode: fixture` is implemented. A future `real-lab` mode may provide another
ScenarioRunner factory/invocation driver, but needs separately authorized scope,
environment credentials and safe target configuration. It is deliberately
rejected by today's schema; no lab adapter or fault injection exists here.

TLS expiry and chain fixtures preserve different certificate facts while the
current engine emits the same generic TLS verification candidate. Redis Storage,
Redis Queues, System Redis and System DB have distinct configured targets; TCP
failure proves connectivity failure only. Protocol-specific root cause remains
inconclusive under existing approved rules. Secret absence uses a controlled
metadata-only unresolved reference; no Secret content is fetched.
